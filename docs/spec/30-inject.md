# 行为规格 · 注入层

> 本层定义"注入什么文本、以什么形态写进去、如何判断已经注入过"。

---

## 1. 注入文本的组装

### 1.1 最终文本的顺序

```
[哈希头行]
[用户自定义人格]      ← 有才写，前后各留一个空行
[政策正文]
[硬化段]
```

- 全部行尾统一为 CRLF。
- 段与段之间恰好一个空行（即两个换行符）。
- 哈希头单独占一行，格式 `<!-- <标记前缀><12位哈希> -->`。

### 1.2 政策哈希

见 `00-overview` 4.2。要点重申：
- 只吃「用户人格 + 政策正文 + 覆盖层」三段，**不吃硬化段**。
- 用户人格为空时按空串参与，不是跳过。
- 末段固定字符串 `False`。

### 1.3 覆盖层的位置

覆盖层（一段带最高优先级声明的文本）的插入位置由目标决定：

| 目标类型 | 覆盖层位置 |
|---|---|
| 整段替换型 | 接在政策正文之后，作为正文的一部分 |
| 标记块型 | 同左 |
| 字段注入型 | 同左 |
| 需要"目标专用段"的 | 专用段接在覆盖层之前 |

### 1.4 目标专用段

部分客户端需要额外一段针对该客户端的说明（例如它有自己的工具调用约定）。

规则：
- 由「目标标识 + 模式」决定要不要加、加哪一段。
- 不加时，正文与通用版本**逐字相同**。
- 加时，专用段与正文之间同样一个空行。

### 1.5 自证段

每个目标的注入文本末尾都带一段"自证口令"：告诉模型在收到某个特定词时回复某个特定串。

规则：
- 自证串 = `破甲已生效｜目标 <短名>｜<版本号>`。
- 短名要短（用户要照着念、照着对）。
- 全称用于横幅，短名用于回执，两者不可混用。
- 版本号取护照里存的**纯数字**版本，不带后缀。

### 1.6 幂等要求

同一份输入连续组装两次，输出必须逐字节相同（哈希相同、段顺序相同、空行数量相同）。

## 2. 三种注入形态

### 2.1 整段替换

**适用**：目标读取的是"一份专门的指令文件"，且该文件可以整体由本工具掌管。

**契约**：
- 写入前先判断"当前内容是不是已经是最新"：
  - 是 → 直接返回"已是最新"，**不重写**。
  - 否 → 先备份（若还没有），再整体写入。
- **不许**采用"先删旧内容、再判断要不要写新的"的顺序。
  该顺序在"已注入且已是最新"的文件上会走到删除，随后因判重跳过写入，导致文件被清空一半。
- 剥离旧内容时，按"从标题行删到下一个同级标题或文末"的方式切；不要用"删到文件末尾"。

### 2.2 标记块

**适用**：目标读取的是用户自己的文件（如 `AGENTS.md`、`CLAUDE.md`），注入内容必须与用户内容共存。

**契约**：
- 文件里没有块 → 追加到末尾（前面补一个空行）。
- 已有块 → 整块替换（含首尾标记）。
- 移除 → 连同首尾标记行一起删；删完若只剩空白：
  - 文件是本工具新建的 → 可删文件；
  - 文件原本就有 → 保留空文件，不删。
- 同一文件里出现多个本工具的块 → 只保留第一个，其余删掉（历史遗留）。
- 块内的行尾跟随文件原有的行尾。

### 2.3 字段注入

**适用**：目标是 JSON 或 TOML 配置文件，只能改某个键的值。

**JSON 契约**：
- 用 `10-io` 5 节的宽松扫描器定位目标键。
- 只替换该键的值，其余字节原样保留（含缩进、键顺序、注释）。
- 值里必须用转义换行（`\n` 的字面形式），**不能**塞真实换行——那会把文件写坏。
- 写后用标准 JSON 解析器复核；解析不过 → 回滚。

**TOML 契约**：
- 键必须落在**顶层**。TOML 里表头之后的键属于该表，直接往文件末尾追加会被吞进最后一张表。
- 顶层位置 = 第一个表头（`[xxx]` 或 `[[xxx]]`）之前。
- 判断表头时要注意：字符串里出现的 `[` 不算，数组值里的 `[` 也不算。用"括号深度为 0 且行首为 `[`"来判定。
- 插入时保留原有空行结构，不重排、不格式化用户配置。
- 移除时严格与插入互逆：插入前什么样，移除后必须一模一样（逐字节）。

### 2.4 三种形态的共同要求

- 写入前必须有备份。
- 写入必须是原子替换。
- 写入后必须回读复核。
- 内容里必须带可识别的标记，使"这是本工具写的"可被判定（见 3 节）。

## 3. 状态判定

对某个目标文件，判定它当前处于哪种状态。三种结果：

| 状态 | 含义 |
|---|---|
| **严格态** | 文件里没有任何本工具写的内容 → 需要注入 |
| **宽松态·当前** | 有本工具内容，且哈希与本次要写的一致 → 无需动作 |
| **宽松态·过期** | 有本工具内容，但哈希对不上 → 默认跳过，`--force` 时重写 |

### 3.1 判定顺序

1. 文件读不到 → 严格态。
2. 内容里没有任何本工具的标记 → 严格态。
3. 有标记：
   - 能取出哈希，且等于期望哈希 → 当前。
   - 否则 → 过期。

### 3.2 "有本工具标记"的判据

用一组关键词判定，任一命中即算：
- 哈希头前缀；
- 政策正文里的特征串（取正文中最不可能与用户文本重合的一段）；
- 自证段的特征串；
- 历史遗留的旧标记（**只读认，不再写**）。

最后一条很重要：机器上可能还留着旧版本写的标记，必须能认出来，否则会重复注入或还原不掉。

### 3.3 过期与重写的取舍

哈希只覆盖政策正文与覆盖层，不含硬化段与自证段。所以：
- 只改了硬化段 → 哈希不变 → 判为"当前" → 不会自动重写。
- 这时由"各目标自己的完备性检查"兜住：缺硬化段就补。

反过来，如果为了让硬化段变化触发重写而把硬化段纳入哈希，会导致所有已注入机器一次性被判过期，白重写几百 KB 到几十 MB 的文件。**明确不这么做。**

### 3.4 跨版本重写

仅看哈希不够：护照里记的版本号与当前版本不一致时，也要重写一遍。

规则：
- 护照不存在 → 重写。
- 护照版本 ≠ 当前版本 → 重写。
- 重写本身幂等，多写一次无副作用。

## 4. 云记忆通道

**背景**：某个客户端有一份"账号级记忆档案"，每轮会话自动进入系统提示词。它是一个独立于主配置文件的注入点。

### 4.1 档案格式

- 一个 Markdown 文件，首部有一行 `> Version: <数字>`。
- 中间有一段 `## Memory Block`，其下是真正进入提示词的内容，段末用 `---` 收尾。

### 4.2 契约

- **读**：取出（用户标识、记忆块内容、版本号、全文）；读不到返回"无"。
- **写**：只替换 `## Memory Block` 段与 `> Version:` 行，其余（用户的其它笔记）逐字保留。
- **移除**：把本工具写的块摘掉，版本行还原或删除；用户自己的内容不动。
- **判定"是不是本工具写的"**：块里带本工具的标记串。

### 4.3 与主配置解耦

云记忆的修补**不能**挂在"主配置有没有变化"上。否则主配置已是最新时，云记忆被客户端清空了也补不回来。

### 4.4 只读保护

部分客户端会把这类文件设为只读。写入前若发现只读：
- 临时去掉只读属性 → 写 → 恢复只读。
- 恢复失败要报出来。

---

## 5. 注入后的可观测结果

成功注入后，磁盘上必须能观察到：

1. 目标文件里出现哈希头与政策正文（或标记块）。
2. 备份文件存在，且内容是注入前的原样。
3. 清单里出现该文件的绝对路径。
4. 护照存在，`persona_hash` 等于本次哈希，`last_action` 为 `apply`。
5. 日志里有一行"已写 <文件>（<字符数> 字符）"。

任何一条缺失都算失败。

---

## 6. 验收要点

- 注入两次，第二次不产生任何字节变化（I1）。
- 注入后撤回，文件字节与注入前完全一致，含 BOM 与行尾（I2）。
- 对已有用户内容的 `AGENTS.md` 注入，用户内容逐字保留（I4）。
- 对带尾逗号/注释的 JSON 注入，其余部分不变，且结果仍可被标准解析器解析。
- 对带多张表的 TOML 注入，键落在顶层；移除后文件与注入前逐字节相同。
- 预演模式下，以上操作全部不落盘（I5）。
