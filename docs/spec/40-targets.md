# 行为规格 · 目标层

> 每个"目标"是一个受支持的客户端。目标层把"注入层"的通用能力适配到各客户端不同的文件形态上。

---

## 1. 目标必须提供的契约

每个目标是一个独立单元，必须能回答以下问题：

### 1.1 身份

| 成员 | 类型 | 说明 |
|---|---|---|
| 短标识 | string | 命令行 `--target` 接受的值，也是护照/清单/参数名的键 |
| 显示名 | string | 界面上给人看的全称 |
| 备份后缀 | string | 该目标所有备份统一使用 |

### 1.2 定位

| 成员 | 说明 |
|---|---|
| 主目录名 | 相对用户主目录的那一层（如 `.codex`）；无则空 |
| 指令文件名 | 主目录下的相对路径 |
| 环境变量 | 可能指向该目标目录的变量名元组 |
| 进程名 | 用于判断"是否正在运行"的进程名元组（含带/不带 `.exe` 两种形式） |
| 可执行文件名 | 用于反查安装根；纯命令行目标留空 |
| 命令行参数名 | 形如 `--<key>-dir`，供用户手动指定 |

### 1.3 行为

| 能力 | 契约 |
|---|---|
| 找候选根 | 按 `20-locate` 的优先级链返回若干候选目录 |
| 判有效 | 给定目录，判断"这里像不像该客户端的家" |
| 解析配置路径 | 从根推出主配置文件的绝对路径 |
| 注入 | 按该目标的形态写入 |
| 撤回 | 从备份还原，逐字节一致 |
| 状态检测 | 返回该目标当前处于哪种状态 |
| 体检 | 返回一组「(级别, 说明, 详情)」行，供只读体检输出 |

**体检行的级别**固定为五种：`ok` / `info` / `warn` / `fail` / `own`（本工具写的）。上层按级别决定颜色与前缀。

### 1.4 附加能力（可选）

- 额外写入：除主配置外还要落的文件（如独立的人格文件）。
- 额外还原：撤回时除主配置外还要处理的文件。
- 专属目录：本工具在该目标下自建的管理目录。
- 云记忆通道（仅部分目标有）。

---

## 2. 三种基类

| 基类 | 适用 | 核心差异 |
|---|---|---|
| **整段替换型** | 目标读一份"专属指令文件"，本工具可整体掌管 | 写入前判"已是最新"；剥离旧内容按标题切 |
| **标记块型** | 目标读用户自己的文件，注入需与用户内容共存 | 只增删自己那一块；文件可能是本工具新建的 |
| **字段注入型** | 目标是结构化配置（JSON/TOML） | 只改一个键，其余字节不动 |

一个目标可以同时具备两种：主配置走字段注入，另落一份整段替换的人格文件。

## 4. DSH 的特殊流程

DSH 的注入目标不是"用户目录下的配置文件"，而是**安装目录里被 Electron 打包进 `app.asar` 的文件**。因此必须先解包。

### 4.1 安装根识别

从候选目录中找"像 DSH 安装根"的位置，判据：
- 存在 `resources/app.asar`，或
- 存在 `resources/app/`，或
- 存在 `node_modules/@deepseek-ai/`（npm 全局安装形态）。

### 4.2 asar 解包

**asar 格式**：
```
[4 字节 头部长度][若干字节 头部 JSON][数据区]
```
- 前 4 字节是小端 uint32，表示头部 JSON 的字节长度（含填充）。
- 头部 JSON 里有一个 `files` 对象，递归描述目录结构；每个文件条目含 `offset` 与 `size`。
- 条目标记 `"unpacked": true` 时，真实内容在旁边的 `app.asar.unpacked/` 目录里。

**契约**：
- 解包到 `<安装根>/resources/app.asar.unpacked/`（与官方解包目录合并，不另建）。
- 文件句柄全程只开一次；几千个文件不能每个都开关一次。
- `unpacked` 标记但 `.unpacked/` 里没有对应文件的条目，回落到 asar 数据区读，**不许静默跳过**。
- 统计成功数与丢失数；有丢失时上层要能据此拒绝后续改名。
- 解包结果要记时间戳；`app.asar` 没更新过就复用，不重复解包。

### 4.3 Electron 保险丝

部分客户端在 `resources/` 下有保险丝配置（`fuses.json` 或二进制哨兵），控制"是否允许从 asar 外加载代码"。

契约：
- 只读判断当前状态。
- 需要时把"只允许从 asar 加载"改成"允许从目录加载"。
- 改之前备份，改之后能还原。

### 4.4 注入点

解包后，注入目标是解包目录里的某个 JS 文件（通常是 CLI 入口）。注入方式为整段替换：找到政策块的位置，整体替换。

### 4.5 还原

1. 从备份还原被改的文件。
2. 若解包目录是本工具建的 → 整个删掉。
3. 保险丝还原。
4. 删除本工具建的专属目录与清单。

## 5. WorkBuddy 的特殊流程

### 5.1 多份模板

WorkBuddy 的政策文本存在多份模板文件里（主模板 + 若干产品模板），每份都要注入。

契约：
- 逐份处理，单份失败不影响其他份。
- 每份都独立备份。
- 统计口径：只数"带政策特征串的模板"，不要把备份和杂项算进分母，否则会出现"几百个靶点零个生效"的假警报。

### 5.2 云记忆

见 `30-inject` 第 4 节。WorkBuddy 与国际版各有一份。

### 5.3 大文件保护

主文件可能有几百 KB 到几十 MB。因此：
- 已是最新时**绝不重写**。
- 过期但用户没加 `--force` 时默认跳过，只在汇总里报"其中 N 个人格哈希来自上一版"。

## 6. ZCode 的特殊流程

### 6.1 系统提示词在 JS 文件里

ZCode 的系统提示词嵌在 `zcode.cjs` 里，是一个 JS 字符串常量。

契约：
- 定位该常量的起止位置（用字符串边界扫描，注意转义）。
- 只替换该字符串的值，其余 JS 代码逐字保留。
- 替换后用 JS 语法检查（若有 node）或至少做括号配对检查；不通过则回滚。

### 6.2 定位文件

`zcode.cjs` 可能不在主目录，需要在若干候选路径里找：
- 主目录下的 `zcode.cjs`
- 主目录下 `dist/`、`lib/`、`bin/` 子目录
- 安装根下的同名文件

找不到时给出"试过哪些路径"的提示。

## 7. 标记块型目标的通用流程

### 7.1 注入

1. 解析配置路径（主目录 + 指令文件）。
2. 目录不存在 → 建（记录"是本工具建的"）。
3. 文件不存在 → 建，写入标记块。
4. 文件存在：
   - 无块 → 追加。
   - 有块 → 整块替换。
5. 备份（首次）。
6. 写后复核。

### 7.2 撤回

1. 有备份且备份里没有本工具标记 → 用备份还原。
2. 否则只删块。
3. 文件删完为空且是本工具建的 → 删文件。
4. 本工具建的目录为空 → 删目录。

### 7.3 状态检测

返回：文件在不在、有没有块、哈希对不对、备份在不在、护照版本是否一致。

---

## 8. 验收要点

- 17 个目标逐个跑"注入 → 再注入 → 撤回"，字节级一致。
- 目标目录不存在时，注入能自建，撤回能删干净（不留空目录）。
- DSH 解包后，注入点文件存在且被正确改写；还原后解包目录被清除。
- WorkBuddy 多模板中有一份失败时，其余仍成功，退出码为 1。
- ZCode 的 JS 文件被改后仍能被 node 解析（若环境有 node）。
